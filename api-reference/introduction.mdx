The Qint merchant API is a small, server-to-server REST API around one resource: the **payment intent**. Create one, redirect the buyer to its `checkoutUrl`, and learn the outcome via [webhooks](/webhooks/overview) or reads.

<Warning>
**20 October 2026:** the payment intent's credit fields changed. `creditUsdt` and `creditAsset` are gone, `creditAmount` and `creditCurrency` are new, and `creditRate` has a new meaning. See the [breaking change note](#breaking-change-20-october-2026).
</Warning>

## Base URL

```text
https://api.qint.ch
```

All endpoints are versioned under `/api/v1`.

<Note>
`api.qint.ch` is the stable production hostname. Keep the base URL in
configuration anyway — environment switches stay a one-line change.
</Note>

## Authentication

Send your `qk_live_…` API key with every request, either way:

```bash
-H "Authorization: Bearer qk_live_…"
# or
-H "X-Api-Key: qk_live_…"
```

Keys carry **Read** and/or **Write** scopes; requests outside a key's scopes return `403`. See [Authentication](/authentication) for creation and rotation.

## Errors

Errors are RFC 7807 problem documents, `Content-Type: application/problem+json`:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "An error occurred while processing your request.",
  "status": 400,
  "detail": "currency must be one of: CHF, EUR, USD, GBP.",
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-00"
}
```

| Status | Meaning |
| --- | --- |
| `400` | Invalid request — bad amount, unsupported currency, a currency Qint has [switched off](/accept-payments/api-payments#currency-availability), malformed `returnUrl`, or an amount outside the [payment limits](/accept-payments/api-payments#payment-limits) (`code: "amount_out_of_range"`). |
| `401` | Missing, malformed, revoked or unknown API key. |
| `403` | Key lacks the required scope (`detail` names it), or new payments are paused because your account has not accepted the [current terms](/accept-payments/api-payments#terms-acceptance) (`code: "terms_acceptance_required"`). |
| `404` | The resource doesn't exist — or belongs to another merchant. |
| `429` | Rate limited — back off and retry. |
| `503` | Exchange rate unavailable (`code: "rate_unavailable"`) — retry in a minute. |

Include the `traceId` when contacting support about a failed request.

### Error codes

Only three errors carry a machine-readable `code`: `amount_out_of_range` (`400`, with `minChf`, `maxChf` and `amountChf`), `terms_acceptance_required` (`403`) and `rate_unavailable` (`503`). Every other error has **no `code` field** — branch on the HTTP status and treat `detail` as a human-readable message.

A currency Qint has switched off for new payments is one of these code-less `400`s:

```json Response (400 Bad Request)
{
  "status": 400,
  "detail": "GBP is currently disabled on Qint. currency must be one of: CHF, EUR, USD."
}
```

(The real response also carries `type`, `title` and `traceId`, as above.) If you need to tell this case apart, match `detail` against `is currently disabled on Qint`. Better: check the public [list currencies](/api-reference/list-currencies) endpoint before creating an intent, so you never send a disabled currency. See [currency availability](/accept-payments/api-payments#currency-availability).

## Rate limits

The API is rate limited per client. On `429`, retry with exponential backoff. Creates are retry-safe — the required `idempotencyKey` makes a replay return the original intent; see [idempotency](/accept-payments/api-payments#idempotency).

## Conventions

- **JSON in, JSON out**, camelCase field names.
- **Statuses are lowercase strings** on the wire: `initiated`, `pending`, `confirmed`, `settled`, `failed`, `expired`, `cancelled`.
- **Crypto amounts are 8-decimal strings** (`"55.48765432"`) — parse as decimals, never floats.
- **Timestamps** are ISO 8601 with offset.
- **Pagination** on list endpoints: `page` (1-based) and `pageSize` (1–100, default 20); responses carry `items`, `total`, `page`, `pageSize`.
- **Ids are prefixed**: intents `pi_…`, payment links `pl_…`, invoices `inv_…`.

## Breaking change 20 October 2026

Merchant balances are now kept in fiat, in each merchant's [Account Currency](/guides/settlement) (CHF, EUR, USD or GBP; CHF by default), instead of a stablecoin. Every payment is credited in that currency at the rate fixed when the buyer is quoted. The base path stays `/api/v1`; the change affects the payment intent and the `payment.status` webhook.

**Payment intents** (`POST /api/v1/intents`, `GET /api/v1/intents`, `GET /api/v1/intents/{id}`):

- **Removed:** `creditUsdt` and `creditAsset`.
- **Added:** `creditAmount` (what the payment added to your balance, 2 decimal places) and `creditCurrency` (your Account Currency at the time of the quote).
- **Changed meaning:** `creditRate` is now units of `creditCurrency` per 1 unit of the invoice `currency`, `1` when they match. It used to be fiat per stablecoin unit.
- **Changed:** `feeAmount` and `netAmount` (still in `currency`) are computed on the quote, so they always agree with the credit. A `settledAmount` booked later no longer changes them.
- All three credit fields are `null` until the payment is credited, and on payments settled before 20 October 2026.

**Webhook** `payment.status`: `creditAmount`, `creditCurrency` and `creditRate` are added (filled on the `settled` event, `null` otherwise). The change is additive; see [credit fields](/webhooks/events#credit-fields).

**SDKs:** `@qint/node` 0.3.0, the .NET package `Qint` 0.3.0, `qint-sdk` for Python 0.3.0 and `github.com/SwizzX-GmbH/qint-go` v0.4.0 follow the change (`credit_amount` and `credit_currency` in Python, `CreditAmount` and `CreditCurrency` in .NET and Go). The WooCommerce plugin 1.0.5 shows the credit in the order note.

**Dashboard:** the balance, balance conversion and Account Currency endpoints are listed under [Dashboard](/api-reference/get-balance) in this reference. Crypto payouts are not offered at launch.
